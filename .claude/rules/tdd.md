# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트별 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.
- 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 유지한다.

## 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 에러 분기)
- **유틸리티 / 순수 함수**
- **버그 수정** (재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (스타일, 레이아웃, 마크업만 있는 컴포넌트)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **적용한다.**

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 설정 오류로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### 2. GREEN — 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 아직 테스트가 요구하지 않는 기능, 옵션, 분기를 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **항상 green을 유지한다.** 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용"으로 남기거나, 주석 처리하거나, 보면서 베끼는 것도 금지**한다. 삭제는 완전한 삭제다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드가 가장 자주 깨진다. 테스트도 단순하니 작성 비용이 거의 없다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현을 그대로 추인할 뿐이며, 실제로는 작성되지 않는다. |
| 시간이 없다 | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 테스트가 시간을 번다. |
| 삭제하면 낭비다 | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이므로 삭제 후 재작성이 더 빠르고 안전하다. |
| 프로토타입이다 | 프로토타입은 그대로 운영 코드가 된다. 버릴 코드라면 테스트를 안 써도 되지만, 이 규칙의 대상(로직, API, 유틸, 버그 수정)이면 적용한다. |
