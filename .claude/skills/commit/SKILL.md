# Commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋으로 남긴다. 별도 승인을 묻지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석
다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff              # unstaged
git diff --staged     # staged
git log --oneline -10 # 최근 메시지 스타일 참고
```

- untracked 파일은 `git status`로 확인하고 필요하면 내용을 읽는다.
- `.env`, 키·토큰, `node_modules`, 빌드 산출물(`dist`) 등 커밋하면 안 되는 파일이 섞여 있으면 제외하고 사용자에게 알린다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- git 저장소가 아니면 그 사실을 알리고 멈춘다. `git init`은 임의로 하지 않는다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 목적의 파일은 묶는다. 예: 컴포넌트와 그 테스트, 스타일 변경 일괄.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 쪼개지 않고 더 큰 목적의 커밋에 함께 넣는다. 대화형 플래그(`git add -p`)는 쓸 수 없다.
- 단위가 하나뿐이면 굳이 쪼개지 않는다.

### 3. 커밋 메시지 작성
형식: `타입: 요약`

| 타입 | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능·UI 추가 또는 변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 스킬 등 기타 |

규칙:
- 요약은 한국어, 50자 안팎, 마침표 없이 "무엇을 했는지" 명사형 또는 `~추가`/`~수정` 식으로 쓴다.
- "수정함", "변경" 같은 모호한 표현을 피하고 구체적으로 쓴다.
- 이유나 맥락이 필요하면 빈 줄 뒤 본문에 한두 줄로 적는다.
- 스코프(`feat(ui):`)는 기존 로그가 쓰고 있을 때만 따른다.
- 시스템 지시에 커밋 끝에 붙일 attribution 줄이 있으면 본문 마지막에 그대로 추가한다.

### 4. 커밋
1. 커밋마다 해당 파일만 명시적으로 `git add <파일>` 한 뒤 커밋한다. `git add -A`와 `git add .`는 쓰지 않는다.
2. 여러 줄 메시지는 heredoc으로 넘긴다.
3. 끝나면 `git log --oneline -n <커밋 수>`로 커밋 메시지와 포함 파일을 요약해 보여준다.

## 금지 사항
- `--no-verify`, `--amend`, `push`, `reset --hard`는 사용자가 명시적으로 요청하지 않으면 쓰지 않는다.
- 훅이 실패하면 원인을 보고 고친 뒤 새 커밋을 만든다. 훅을 우회하지 않는다.
- 현재 브랜치가 `main`/`master`이면 커밋 전에 새 브랜치를 만들어 그 위에 커밋한다.

## 예시

```
feat: 레트로 데스크톱 창 스타일로 전체 UI 개편
fix: API 키가 없을 때 생성 버튼이 활성화되던 문제 수정
refactor: useComponentGenerator의 에러 처리 분리
chore: commit 스킬 추가
```
